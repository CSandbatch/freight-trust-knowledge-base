### Recommended synthetic-experiment design (Aim 2)

No single freight-specific dataset exists. The most defensible, immediately buildable design combines two real, free, currently maintained tools:

1. **Generate the base event sequence** using the OpenEPCIS Test Data Generator (Apache 2.0, actively maintained) configured to emit the Aim 2 schema's fields — event type (aligned to appointment/arrival/gate/dock/departure), source system, submitting party, capture timestamp, permitted-use tag, confidence/verification status — styled as EPCIS-like events. Optionally cross-check plausible inter-event time distributions (transit/dwell) against the real, free BTS ATRI Freight Mobility Initiative county-to-county truck travel-time data (data.bts.gov), so synthetic timing is not arbitrary.
2. **Inject labeled tampering/contradiction cases** following the process-mining field's established methodology (as used in the Process Discovery Contest 2020/2021 benchmarks and the Nolle et al. synthetic-log tradition): take a "clean" base log, apply the four threat classes the draft already names in Section 4 (single-party fabrication, backdated timestamp, replay/silent edit, selective omission) to a defined percentage of traces, and retain ground-truth labels for which traces were altered.
3. **Measure detection rate and false-alarm rate** of a candidate cross-source discrepancy/correlation check against this labeled set — this is a direct, controlled test of the Aim 2 hypothesis and requires no external data-sharing agreement, no paid license, and no partner commitment.
4. **Test the correction workflow** by scripting a dispute against a subset of records and measuring elapsed time to a corrected/annotated record and downstream context update, per Section 4's experiment design — this is buildable entirely in-house against the synthetic corpus.

**What still requires a real partner/permission:** validating this synthetic pipeline against *actual* facility event data would require either (a) a signed ATRI data-sharing agreement (restricted, not self-service) for real truck-GPS ground truth, or (b) a live pilot-interest partner with credentialed access to a real terminal-appointment API such as APM Terminals' or Port Houston's (both are documented, both require registration/partner status, neither is free public bulk data). Absent that, Phase I's Aim 2 result is necessarily a synthetic-benchmark feasibility result, not a real-data validation — which is consistent with how the draft already scopes Aim 2 ("simulated and permissioned event data," Section 6).

### Recommended synthetic-experiment design (Aim 3)

1. **Stand up the NIST Policy Machine** (`usnistgov/policy-machine-core` + `policy-machine-pdp`) as the actual attribute-based policy-enforcement engine for the Aim 3 prototype, configured with freight-specific attributes for partner type (carrier/broker/facility), field category (identity, insurance, telematics, event-summary), and purpose (onboarding verification, dispute resolution, etc.).
2. **Author an automated enforcement test suite in the OASIS XACML conformance-test format** (policy, request, expected-decision triples) — adapting the same structural pattern AT&T/OASIS used, but with freight-specific disallowed combinations drawn directly from Section 5's own examples (a facility receiving a carrier's unrelated insurance-rate data; a broker receiving raw telematics beyond a permitted event summary). Run this suite against the Policy Machine to produce the 100%-denial / 100%-audit-capture structural result Section 5 and the Section 7 milestone table already target — this requires no external data at all, since it is a synthetic, structural test by design.
3. **Implement the audit log** as an append-only or hash-chained log recording requester, purpose, decision, and timestamp for every access event in the test suite, per Section 5's "audit design" — again fully synthetic and buildable without partner data.
4. **For the redress prototype**, script a challenge case and measure elapsed time to a visible correction, using the FCRA 30-day statutory dispute window and the Oversight Board's overturn-rate/appeal-volume reporting as *framing precedents* for how to define and report a correction-latency ceiling (not as data to import) — the actual number remains a Phase I output.
5. **Treat Flower/FedML and the NIST DP Synthetic Data Challenge assets as optional stretch components**, only if Phase I wants to additionally demonstrate a cross-party computation (not just gated access) or test one specific privacy-leakage class using an established methodology — neither is required to meet Aim 3's core go/no-go criterion.

**What still requires a real partner/permission:** none of the above requires a real freight partner — this is the one aim where a fully synthetic, structural Phase I demonstration is achievable using entirely open, government- or standards-body-maintained tooling. The one open gap this scan cannot resolve is the **data-sharing incentive/participation mechanism** (GOALS.md G7/G12, still ⚪ not started) — none of the federated-learning benchmarks found (LEAF, FedML, Flower) address *why* a carrier or broker would participate; they are technical-computation benchmarks, not adoption-economics research. That remains a genuinely open question requiring either primary interviews or an adjacent-industry precedent (e.g., banking KYC utilities), not a dataset this scan could locate.

## Summary for whoever reads only this section

- **Aim 2**: no freight-specific facility-event benchmark exists anywhere (confirmed, not merely undiscovered). The best buildable path combines the open-source OpenEPCIS event generator with the process-mining field's established labeled-anomaly-injection methodology (as used in the Process Discovery Contest benchmarks), optionally calibrated against BTS's free, ATRI-derived county-to-county truck travel-time data for realistic timing.
