### Recommended synthetic-experiment design (Aim 2)

No freight-specific public dataset was located in the documented search as of 2026-08-18. The most defensible, immediately buildable design combines public standards, project software, and clearly labeled synthetic choices:

1. **Generate the base event sequence** using the OpenEPCIS Test Data Generator (Apache 2.0, actively maintained) configured to emit the Aim 2 schema's fields — event type (aligned to appointment/arrival/gate/dock/departure), source system, submitting party, capture timestamp, permitted-use tag, confidence/verification status — styled as EPCIS-like events. Optionally cross-check plausible inter-event time distributions (transit/dwell) against the real, free BTS ATRI Freight Mobility Initiative county-to-county truck travel-time data (data.bts.gov), so synthetic timing is not arbitrary.
2. **Inject labeled alterations/contradictions** using BINet as precedent for artificial anomaly operators; use PDC only for hidden-truth/conformance design. Freight fabrication, backdating, replay, silent edit, clock, and omission operators are project-authored threat-model choices. Omission is evaluated at trace level under observability truth, not as a `missing` event.
3. **Measure detection rate and false-alarm rate** of a candidate cross-source discrepancy/correlation check against this labeled set — this is a direct, controlled test of the Aim 2 hypothesis and requires no external data-sharing agreement, no paid license, and no partner commitment.
4. **Test the correction workflow** by scripting a dispute against a subset of records and measuring elapsed time to a corrected/annotated record and downstream context update, per Section 4's experiment design — this is buildable entirely in-house against the synthetic corpus.

**What still requires a real partner/permission:** validating this synthetic pipeline against *actual* facility event data would require either (a) a signed ATRI data-sharing agreement (restricted, not self-service) for real truck-GPS ground truth, or (b) a live pilot-interest partner with credentialed access to a real terminal-appointment API such as APM Terminals' or Port Houston's (both are documented, both require registration/partner status, neither is free public bulk data). Absent that, Phase I's Aim 2 result is necessarily a synthetic-benchmark feasibility result, not a real-data validation — which is consistent with how the draft already scopes Aim 2 ("simulated and permissioned event data," Section 6).

### Recommended synthetic-experiment design (Aim 3)

1. **Stand up the NIST Policy Machine** (`usnistgov/policy-machine-core` + `policy-machine-pdp`) as the actual attribute-based policy-enforcement engine for the Aim 3 prototype, configured with freight-specific attributes for partner type (carrier/broker/facility), field category (identity, insurance, telematics, event-summary), and purpose (onboarding verification, dispute resolution, etc.).
2. **Author a neutral authoritative case tuple**, including authority and expected native decision, then compile it into separate NGAC/PML and XACML lanes with tested domain-decision adapters. Do not claim cross-standard conformance from a shared file format.
3. **Secure and instrument the enforcement path**: require validated JWT issuer/audience/signature/expiry and subject binding; disable `none` authentication and sandbox bypass; capture at the PEP and reconcile every request, error, timeout, and response to an independent request ledger. Treat a hash chain as narrow alteration evidence under a declared anchoring/truncation model.
4. **For the redress prototype**, script a challenge and measure propagation to every authorized view while retaining superseded history. Use FCRA only as adjacent evidence that authority, notice, reinvestigation, and correction rules must be explicit; do not import its time period.
5. **Treat Flower/FedML and the NIST DP Synthetic Data Challenge assets as optional stretch components**, only if Phase I wants to additionally demonstrate a cross-party computation (not just gated access) or test one specific privacy-leakage class using an established methodology — neither is required to meet Aim 3's core go/no-go criterion.

**What still requires a real partner/permission:** the synthetic structural lane does not require a freight dataset, but authoritative freight-policy rules, contract/jurisdiction interpretations, production authentication, independent review, and partner-facing validation are real dependencies. The toolchain also includes project-authored adapters and corpus, not only government/standards artifacts. The participation/incentive mechanism remains an open question requiring stakeholder research rather than a technical dataset.

## Summary for whoever reads only this section

- **Aim 2**: the documented public-source search located no freight-specific facility-event benchmark. The build path combines GS1 semantics, version-pinned OpenEPCIS generation, project-authored freight operators, BINet anomaly precedent, PDC hidden-truth precedent, and BTS travel-time calibration. That is synthetic feasibility, not partner validation.
- **Aim 3**: NIST Policy Machine and OASIS XACML support separate implementation lanes; neither makes the other conformant. Secure authentication, decision mapping, PEP capture, an authoritative oracle, and privacy controls remain project work and all hypotheses are unrun.
- **Access constraints found**: ATRI raw GPS is agreement-gated and PIERS is commercial. These are bounded retrieval/access findings, not proof that no private corpus exists.
