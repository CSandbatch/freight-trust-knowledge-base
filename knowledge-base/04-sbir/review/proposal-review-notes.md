## 2. Blocking findings

Must be fixed before this package is client-ready.

1. **Two beachhead workflows in scope at once — direct contradiction of NSF guidance and of the vault's own docs.**
   - **Files:** `phase-1-project-description-draft.md` §1 and §6; `commercialization-plan-draft.md` §1; `project-pitch-draft.md` §3 (Market Opportunity).
   - **Problem:** The Project Description states in §1, "This Phase I proposal targets two bounded instances of that problem" — (a) carrier onboarding/identity verification and (b) disputed facility events — and §6 confirms both are integrated into one bounded pilot ("the two bounded workflows named in Section 1"). The Commercialization Plan still has an **unresolved placeholder** in §1: `[WORKFLOW PLACEHOLDER — select one: carrier onboarding/identity verification, OR disputed facility-event (detention) evidence handling. ... pick one testable workflow, not all of them.]` — directly quoting the Guide's own instruction to pick one. The Project Pitch's Market Opportunity section splits the difference, naming a primary buyer and then calling facility-event evidence "a connected beachhead," which reads as a second workflow without resolving which one is primary.
   - **Consequence:** The Guide (§8, item 2) is explicit: "Choose the beachhead. Pick one initial, testable workflow... rather than attempting all freight trust problems at once." Running two workflows through three research aims in a 12-month, ≤$305K Phase I is exactly the breadth-over-depth failure pattern a skeptical reviewer will flag under Intellectual Merit (unfocused hypothesis) and Commercial Potential (no single first buyer). The contradiction changes the actual R&D scope, the budget's FTE math, and the pilot design in Project Description §6. It is not a stylistic inconsistency.
   - **Fix:** Pick one workflow (the evidence base and stakeholder friction favor carrier onboarding/identity verification as primary, per the master brief's stakeholder-landscape framing already cited in the Commercialization Plan). Rewrite Project Description §1 and §6 to scope the bounded pilot to that single workflow, demote the other to "Phase II expansion candidate," and resolve the Commercialization Plan §1 placeholder to match. Update the Project Pitch's Market Opportunity paragraph to drop "connected beachhead" framing unless it is explicitly scoped as future work, not Phase I scope.

2. **Detention cost figure ($3.6B + $11.5B = $15.1B split) cited with unwarranted year-specificity that SBIR Evidence Refresh explicitly flags as unverified/possibly stale.**
   - **Files:** `phase-1-project-description-draft.md` §1(b); `commercialization-plan-draft.md` §2 (Quantified pain table, "Detention-related cost and hours" row).
   - **Problem:** Both drafts attribute "39.3% of stops involved detention, 135.9 million lost hours, $3.6 billion in direct expenses, and $11.5 billion in productivity losses" to **"ATRI's 2023 analysis."** `sbir-evidence-refresh.md` (market evidence item 6) independently checked this exact $15.1B-equivalent figure and found it "**may trace to an older ATRI detention study (circa 2019–2020)**, not confirmed as restated in the 2025 Operational Costs Update specifically... Do not attribute this figure to 'ATRI 2025' without confirming it appears in the current-year report — it may be a stale number being recirculated as if current." The drafts' "2023" label is exactly the kind of unwarranted-currency citation the refresh warns against. `evidence.md` also repeated the "2023 analysis" label, but without an independent freshness check; the later evidence-refresh pass is the controlling freshness review and requires the year-specific attribution to remain softened until the primary ATRI report is re-read.
   - **Consequence:** This is the single most load-bearing "why now" cost figure in the Problem/Significance section and the Commercialization Plan's pain table. If a reviewer or program officer traces the citation and finds it is actually a ~2019–2020 study being presented as current, it damages the whole document's credibility on fact discipline — a fatal problem for an NSF reviewer already primed to distrust unsupported market claims (Guide §6 failure patterns).
   - **Fix:** Before this figure is used again, verify against the primary ATRI PDF (not trade-press paraphrase) which year/report it actually comes from. Until verified, either (a) drop the "2023" label and cite it generically as "an ATRI industry estimate, vintage unconfirmed — verify before submission," or (b) replace it with the separately-verified 2025 ATRI Operational Costs figures (non-fuel marginal cost $1.779/mile, dwell time ~1h38m — noting the 1h38m vs 1h49m discrepancy also flagged in the refresh) if those better serve the point being made.

3. **TABA is described using the outdated (pre-2026) "separate supplement" model instead of the current "inside the $305K cap" mechanism.**
   - **Files:** `phase-1-budget-and-justification-draft.md`, "Technical and Business Assistance (TABA) — flag only, not budgeted here" section; `commercialization-plan-draft.md` §8 ("Bridge / non-dilutive" row cites the same section).
   - **Problem:** The Budget draft states: "NSF SBIR/STTR programmes have **historically permitted** an additional Technical and Business Assistance allocation, **separate from and in addition to** the Phase I award ceiling... no TABA line is included in the total above." `sbir-evidence-refresh.md` confirms the opposite is now true: "TABA is up to **$6,500 for Phase I**, and it must be **budgeted within the base Phase I proposal**, not requested as a separate post-award supplement the way some older NSF guidance (an archived 2020 NSF document, `nsf20-070`) described." The nsf.gov solicitation page directly states the $305,000 figure "encompasses all direct and indirect costs as well as the small business fee, [TABA], and the optional... I-Corps."
   - **Consequence:** If the company (or a fixer agent) builds the real budget using this draft's framing, they will likely omit TABA entirely or attempt to request it as an add-on. That is not how NSF 26-510 works. The result is an error at the compliance-review stage, not just a missed opportunity.
   - **Fix:** Replace the "flag only, not budgeted here" section with a real line item: "G. Other direct costs — Technical and Business Assistance (TABA)," up to $6,500, budgeted inside the $305,000 total, with a justification sentence (e.g., funds external market-research or IP-protection assistance). Update the Two-Thirds Small-Business Share Check to confirm TABA spend is treated correctly in that calculation (TABA is typically excluded from the small-business-performed-R&D-share test since it funds external assistance — confirm this against the current PAPPG before finalizing). Update the Commercialization Plan §8 cross-reference so it no longer describes TABA as a "bridge" funding source outside Phase I.

4. **Phase I work-plan diagram (07) contains a Gantt task dated before the project start.**
   - **File:** `07-visuals/07-phase1-work-plan.mmd`, line 31: `Phase I final report : report_2, 2027-06-15, 30d`.
   - **Problem:** Every other section in the same file starts at `2027-07-01`. The final report task is dated `2027-06-15` — a full year (minus two weeks) *before* the project start date, and before every dependent task it should follow (it should logically come after `report_1` / after all Aims and Integration complete, i.e., near month 12, around mid-2028). This is a hard scheduling-logic defect, not just an "illustrative dates" caveat — the note on the chart ("dates illustrative; shift to award start") explains that the whole timeline can be shifted, but it does not explain a task landing chronologically before its own dependencies and before the project start.
   - **Fix:** Change `report_2` to a real relative date, e.g. `after integ_3, 30d` (so it correctly follows pilot evaluation) or an explicit date one year later (`2028-06-15, 30d`) consistent with the other 12-month-out dates in the file.

5. **Work-plan diagram (07) schedules all three Aims and Integration in parallel from day one, contradicting the Project Description's explicit staggered dependency chain.**
   - **Files:** `07-visuals/07-phase1-work-plan.mmd` (Aim 1/2/3 sections all start `2027-07-01`; Integration section starts `2027-10-01`, a fixed date, not an "after" dependency); `phase-1-project-description-draft.md` §7 work-plan table.
   - **Problem:** The Project Description's Section 7 table explicitly sequences work: Aim 3 doesn't start until Months 6–9 ("Aim 1 and Aim 2 components stable enough to integrate" is its stated dependency), and the "Integrate components into the bounded-pilot pipeline" activity is Months 9–11, dependent on "Aims 1–3 individually meeting go/no-go criteria." The diagram instead starts Aim 1, Aim 2, and Aim 3 all simultaneously on the same day, and starts Integration at a fixed calendar date (`2027-10-01`, ≈ month 3) rather than after the Aims' go/no-go gates. This is not a simplification — it depicts a materially different (and less credible) project plan: integrating unvalidated components at month 3 instead of after month 9 gating.
   - **Fix:** Rebuild the Gantt using `after` dependencies that mirror Project Description §7: e.g., Aim 3's tasks should start `after a1_2` or a similar proxy for "Month 6," and Integration tasks should start `after a3_3` (or equivalent), not on a fixed early date. Consider adding milestone markers (`milestone` type in Mermaid Gantt syntax) for the six go/no-go checkpoints named in Project Description §7, so the diagram and the milestone table are traceable to each other.

6. **Budget draft's own eligibility math cannot be evaluated, but the draft does not flag the likely-heavy external-role structure implied elsewhere in the package as a two-thirds-share risk.**
   - **Files:** `phase-1-budget-and-justification-draft.md`, "Two-thirds small-business R&D share check" section; `phase-1-project-description-draft.md` §8 (Team and resources — lists a Domain/freight SME consultant *and* a Legal/privacy advisor as separate external roles); `technical-risk-register.md` ("SBIR/STTR budget-share and lane risk" row).
   - **Problem:** The Project Description's team table (§8) lists two potentially-external roles (domain SME "consultant or subaward" and a legal/privacy advisor, which is very often an external counsel engagement) in addition to a possible STTR research-institution subaward mentioned in the Budget's "Other direct costs" row. None of the docs currently sum a rough worst-case external-cost percentage to sanity-check the two-thirds rule before scope is finalized — the Budget's check table is entirely `[CALCULATE ONCE RATES ARE REAL]`.
   - **Consequence:** This is flagged correctly as a risk in the Technical Risk Register, but the Budget draft — the document that should operationalize it — takes no preliminary action, deferring the entire check to a future date with no interim safeguard. If a fixer builds a real budget without first doing a rough external-cost estimate, the two-thirds violation could be discovered too late.
   - **Fix:** Add a rough-cut placeholder calculation now (e.g., "external roles [consultant + legal/privacy advisor + any subaward] should be planned to stay under approximately $[X] of a $305,000 total to preserve headroom under the two-thirds rule; confirm once real rates exist") so the constraint is visibly load-bearing during team/role planning, not only checked after the fact.

7. **GAO citations (GAO-12-364, GAO-16-401R) used as primary-source evidence in three of the six drafts fall outside the two ground-truth files this review was scoped against, and have not been independently re-verified in the same pass that flagged other stale/unverified figures.**
   - **Files:** `phase-1-project-description-draft.md` §1(a), §3, §9; `commercialization-plan-draft.md` §2; `technical-risk-register.md` (Adversarial/manipulated records row).
   - **Problem:** These citations trace to `03-research-evidence/luna-wide-net-synthesis.md` and `01-client-briefs/freight-trust-client-master-brief.md`, both of which give real gao.gov URLs — they are not fabricated. But they do **not** appear in `evidence.md` (the evidence register) or `sbir-evidence-refresh.md` (the freshness-check file), which are the two files this review was instructed to treat as ground truth. Unlike the ATRI/NSF facts, these GAO report numbers have not been through the same "recheck current sourcing" pass that caught the TABA and detention-figure problems.
   - **Consequence:** The Project Description's own evidentiary-basis note (header) claims every factual claim is "sourced to `evidence.md` or `03-research-evidence/luna-wide-net-synthesis.md`" — which is technically true — but this review's ground-truth scope (evidence.md + sbir-evidence-refresh.md) doesn't cover luna-wide-net-synthesis.md, so these citations haven't had the same scrutiny as everything else in this review. Given that this same research programme's evidence-refresh pass already caught two stale/misattributed figures (TABA process, ATRI detention year), a GAO report number or holding could plausibly also be slightly mis-cited (e.g., GAO-16-401R's exact 99.1% figure and its actual subject matter should be independently reread before submission).
   - **Fix:** Before submission, have someone directly open both GAO reports at the cited URLs and confirm the specific figures (99.1% small-business share; historical FMCSA identity-evasion detection limits) are accurately paraphrased and still the most current GAO figures on these points, the same way SBIR Evidence Refresh did for the NSF solicitation facts.

8. **Submission-map diagram (08) presents "Commercialization Plan" as a required, coequal Research.gov proposal document without confirming that against the Guide's own document list, and omits two documents the Guide does list.**
   - **File:** `07-visuals/08-sbir-submission-map.mmd`, node D4 ("Commercialization Plan") alongside D1–D3, D5–D7.
   - **Problem:** The Guide's §5 core-package list is: "the standard cover and certifications, project summary, project description, references, budget and justification, facilities/resources, senior/key-personnel materials, data-management plan, letters and supplementary documents where applicable, and the Project Pitch invitation." A standalone "Commercialization Plan" as a distinct uploaded Research.gov document is **not** in that list — Commercial Potential content is normally addressed inside the Project Description narrative for NSF SBIR Phase I (unlike some other agencies' SBIR programs, which do require a separate commercialization plan document). The diagram also omits "Project Summary" and "Facilities/Resources," both of which the Guide does list as required core-package items.
   - **Consequence:** If read literally, the diagram tells a proposal-production team to expect a separate Research.gov upload slot for "Commercialization Plan" that may not exist, while not surfacing two slots that do exist — a planning-accuracy risk for whoever uses this diagram to build the Research.gov submission checklist.
   - **Fix:** Verify against current Research.gov instructions at invitation time whether Commercial Potential content is submitted as a standalone document or embedded in the Project Description; adjust node D4's label accordingly (e.g., "Commercialization content (embedded in Project Description, per current instructions)" if that's confirmed). Add Project Summary and Facilities/Resources nodes so the diagram matches the Guide's full core-package list, or add a caption noting the diagram shows only the vault-authored supporting drafts, not the complete NSF-required document set.

9. **"Invitation valid for two deadlines" is presented as settled fact in the submission-map diagram without the hedge SBIR Evidence Refresh applies to the same claim.**
   - **File:** `07-visuals/08-sbir-submission-map.mmd`, node B: `"Invitation\nvalid for 2 deadlines"`.
   - **Problem:** `sbir-evidence-refresh.md` explicitly downgrades this specific mechanic to "Partially verified — flag for manual check," noting that two direct fetches of the current NSF pages "did not surface an explicit 'valid for two deadlines' sentence, only a specific worked example," and recommends "a manual visit to confirm the exact current wording before relying on it in planning language." The diagram states it flatly, with no hedge, in a document that will likely be used directly in planning conversations (exactly the use the refresh warned about).
   - **Fix:** Either add a footnote/annotation to the diagram flagging this as "mechanism corroborated, exact current wording unconfirmed — verify at seedfund.nsf.gov before relying on for scheduling," or hold the claim as-is only until the manual verification SBIR Evidence Refresh recommends has actually been done, and note that it has been done once confirmed.

## 3. Improvement findings

Non-blocking but valuable.

1. **Project Pitch — Market Opportunity section has no buyer-specific quantification.** (`project-pitch-draft.md` §3) The section leans on the Montgomery ruling (a legal driver, correctly caveated) but includes no dollar figure specific to the buyer's own workflow cost — every quantified figure is industry-level. Once discovery interviews produce even directional numbers (hours spent per onboarding decision, cost per disputed detention claim), add one buyer-specific figure here; it will materially strengthen Commercial Potential persuasiveness without inventing anything.

2. **Project Pitch — Company and Team field is only 65% of its character limit, almost entirely placeholder scaffolding.** (`project-pitch-draft.md` §4) This is correctly flagged in the draft's own footnote as deliberate ("expand only with true, confirmed facts"), but a reviewer will read a thin, generic Company/Team field as a weak signal on "can this team execute" even after brackets are filled, if the filled-in content stays at the level of role titles instead of real differentiating background. Recommend the eventual fill-in include one concrete, verifiable credential or track-record sentence per named person, not just a role label.

3. **Project Description — Aim 1's baseline comparator is still an open bracket, making the central "beats a defined baseline" claim currently unfalsifiable as written.** (`phase-1-project-description-draft.md` §2/§3: "current manual/rules-based verification workflow [and specific point-solution comparators to be named once data access is confirmed]") Name at least one concrete point-solution comparator (even provisionally, e.g., "a representative rules-based MC/DOT lookup workflow") before the next draft pass, since "beats an unnamed baseline" is not a testable hypothesis yet.

4. **Project Description §9 (Broader Impacts) defers all equity evidence to future measurement with no current small-carrier engagement signal.** Recommend committing now to a concrete small-carrier interview quota within the planned 5–10 discovery interviews (e.g., "at least 3 of the discovery interviews will be with carriers below [fleet-size threshold]"), so the equity commitment is operational pre-submission, not only a Phase I output.

5. **Budget draft is entirely placeholders with no rough plausibility check of aggregate FTE cost against the $305K ceiling.** Recommend a back-of-envelope sum (even with illustrative market-rate salary assumptions) to confirm the proposed role structure (PI + 2 senior roles + engineer(s) + consultant + legal advisor + cloud/data costs) is achievable within $305K over 12 months before the real budget is built — catching an infeasible scope now is cheaper than catching it after milestones and team roles are locked into the Project Description.

6. **Data Management Plan — every data source row in §1 and every retention period in §4 is an unfilled bracket with no provisional default.** Unlike some other placeholder fields in this package, retention periods and encryption/storage controls (§4, §5) are things the company could state a reasonable default for even before partner agreements exist (e.g., "retained through award period plus [X] years, per standard federal audit-retention practice, unless a partner agreement specifies shorter"). Recommend filling these with defaults now and only bracketing the partner-specific overrides.

7. **Data Management Plan has zero named, even provisional, data sources anywhere.** (§1, every row: `[SOURCE PLACEHOLDER]`) A DMP that is entirely hypothetical is a weaker Broader-Impacts/Intellectual-Merit signal than one anchored to at least one concrete, lawfully-obtainable source (even a public registry). Recommend identifying at least one real, nameable data source before the next draft.

8. **Commercialization Plan §2 quantified-pain table is entirely empty of buyer-specific figures.** Every pain-dimension row that should carry a number is `[QUANTIFIED PAIN PLACEHOLDER]`. Given `evidence.md` G9 references "four exploratory interviews" already conducted (status "not web-researchable — direct question to user/team"), reconcile whether any directional figures from those four interviews can be used now, even provisionally, instead of leaving every cell blank.

9. **Commercialization Plan §9 checklist does not cross-reference the Pitch draft's G9 reconciliation note.** The Project Pitch's "Facts required before submission" table explicitly flags: "status of G9's 'four exploratory interviews' should be confirmed and reconciled with this count." The Commercialization Plan's own "Commercial evidence still required" checklist (§9) doesn't mention this reconciliation at all, creating a gap where the two documents could end up with different interview counts if each is updated independently.

10. **Technical Risk Register — "Integration risk" row's Phase I experiment/control is noticeably more generic than the other rows.** ("Test within a named, bounded workflow... with defined deployment assumptions and a measurable operational outcome" — no specific falsifiable test named, unlike the Aim 1/Aim 2 rows which specify precision/recall, calibration error, detection rate, etc.) Recommend adding a concrete integration test criterion (e.g., a defined pass/fail threshold on end-to-end pipeline completion rate across the adjudicated benchmark).

11. **Technical Risk Register has no row for the two-workflow scope/schedule risk identified in Blocking Finding #1.** Once the beachhead-workflow contradiction is resolved, add (or retire, if resolved to one workflow) a risk row explicitly addressing schedule/scope risk from running multiple workflows in parallel, since this is currently an unmanaged risk that isn't visible anywhere in the register despite being visible in the Project Description's actual plan.

12. **Diagram 06 (technical architecture) — the Decision Output → Abstention → Confidence Score → Correction Loop arrow sequence reads as if abstention/confidence scoring happen after the decision, inverting the drafts' framing.** The Project Description and Pitch both describe calibrated confidence and abstention as *intrinsic to forming* the decision output ("producing a confidence estimate rather than a binary match and abstaining... rather than forcing a decision"), not as a downstream step. Recommend reversing the arrow order so Confidence/Abstention feed into Decision Output, which then feeds the Correction Loop.

13. **Diagram 07's title/caption commits to a specific illustrative start date (`2027-07-01`) without noting which NSF deadline it's keyed to, or whether it's realistic given the Guide's own "4 March 2027 is the prudent base case" planning target.** A `2027-07-01` award start assumes an unusually fast turnaround from a March 2027 deadline (NSF review/award timelines typically run several months past a deadline). Recommend adding a one-line caption noting this is illustrative and does not represent the Guide's own realistic award-start estimate, to avoid the diagram being read as a schedule commitment.

14. **Placeholder/outstanding-items checklist format is inconsistent across the six drafts (stylistic only).** The Pitch draft uses a table ("Facts required before submission"); Project Description uses a table ("Placeholder register"); Budget, DMP, Commercialization Plan, and Risk Register use a Markdown checkbox list ("Facts needed from company" / "Commercial evidence still required"). Not a substantive problem, but harmonizing format would make it easier to build one master "submission-readiness" checklist across all six documents.
